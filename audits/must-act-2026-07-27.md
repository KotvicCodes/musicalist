# Musicalist audit, 2026-07-27

Audited at `39f663c` on `main`, version 1.1.3. Baseline: `npm test` passes 119/119,
`npm run lint` clean. Nothing here is a build break; these are correctness, resilience,
hardening and coverage gaps.

Severity is what it costs the user, not how hard it is to fix.

---

## Must act

### 1. CSV export is open to spreadsheet formula injection

**Severity: high (security)**
**File: `src/export.js:66`**

`escapeCell` implements RFC 4180 quoting only. A value beginning with `=`, `+`, `-`, `@`,
tab or CR is written verbatim, and Excel, LibreOffice and Numbers evaluate it as a formula
on open.

The values are not user-authored. MusicBrainz genres and tags are community editable, which
`src/index.html:7` already names as a live attack surface and defends against for the HTML
path via `escapeHtml`. The CSV path is the untreated sibling: a tag reading
`=HYPERLINK("http://attacker","Play")` reaches the exported file intact, and Deezer titles
routinely start with `-` legitimately, so the case is reachable without any attacker at all.

Suggested fix: in `escapeCell`, prefix a leading `=+-@\t\r` with a single quote, or wrap the
cell in quotes with a leading tab. Both defeat evaluation; the apostrophe form is more common
and reads better in the cell. Add a test per dangerous prefix, plus one asserting a legitimate
leading `-` (a title like `-Ame-`) still round-trips readably.

Not auto-fixable per the skill's rule: security findings need a human to confirm the fix
covers the whole class and does not just mask the obvious case.

### 2. No timeout on any network request, so a stalled connection hangs the run forever

**Severity: high**
**Files: `src/api/deezer.js:72`, `src/api/musicbrainz.js:55`, `src/api/acousticbrainz.js:74`**

All three clients call `fetch(url)` with no `AbortSignal`. Node's fetch has no default request
timeout. A connection that opens and then goes silent (captive portal, dropped route, a service
holding the socket) never rejects, so:

- the throttle queue in that module is blocked behind the pending promise forever,
- `lookupSongs` never returns, so the `run-lookup` IPC handler never settles,
- the renderer's Proceed button stays disabled with `Looking up N songs…` on screen permanently,
- the only way out is quitting the app, and every row already streamed is lost.

Suggested fix: `AbortSignal.timeout(...)` on each fetch. Deezer's failure is fatal to the run,
so it should map to `DeezerError` with `kind: 'network'`; MusicBrainz and AcousticBrainz already
swallow everything to `null`, so a timeout there degrades to a row without genres, which is the
correct behaviour. Suggest 15s for Deezer and MusicBrainz, 10s for AcousticBrainz. Test with a
fetch stub that returns a promise which never settles and assert the call rejects or resolves
null within the budget.

### 3. The one error the user actually sees is mangled by Electron's IPC wrapper

**Severity: medium**
**Files: `src/renderer.js:80`, `src/index.js:60`**

`lookupSongs` deliberately rethrows only `kind === 'network'`, and `deezer.js:74` writes a clear
message for it: `Could not reach Deezer. Check your internet connection.` But an error thrown
inside `ipcMain.handle` is re-serialised by Electron, and `ipcRenderer.invoke` rejects with the
message prefixed by its own framing. What lands in `statusQ` is roughly:

```
Something went wrong: Error invoking remote method 'run-lookup': DeezerError: Could not reach Deezer. Check your internet connection.
```

The carefully written sentence is real but buried behind implementation noise, and this is the
single failure path a user is most likely to hit (unplugged wifi mid-run).

Suggested fix: have the `run-lookup` handler catch and return a result envelope
(`{ ok: false, message, kind }`) rather than throwing across the IPC boundary, and have the
renderer read `message` directly. This also gives a place to distinguish `rate-limit` from
`network` in the UI copy, which the `kind` field already supports and nothing currently uses.

### 4. A run cannot be cancelled

**Severity: medium**
**Files: `src/renderer.js:59`, `src/api/lookup.js:79`**

The README budgets two to three seconds per song and says a hundred-song list takes a few
minutes. There is no stop control. Once Proceed is clicked the button is disabled until the
loop finishes, and a paste of the wrong list, or a run started before noticing a typo, has to
be waited out or the app killed. Killing it discards every row already collected, since the
renderer holds them only in memory and export is only reachable after the fact.

Suggested fix: thread an `AbortSignal` from a Stop button through `run-lookup` into
`lookupSongs`, checked at the top of each loop iteration and passed to the fetches from finding 2.
Rows already streamed stay on screen and stay exportable, which is the main point.

### 5. Deezer's top hit is accepted with no verification that it is the song asked for

**Severity: medium (accuracy)**
**File: `src/api/deezer.js:197`**

`searchTrack` sends `limit=1` and takes `items[0]` unconditionally. There is no comparison
between the query and the returned title or artist. A misspelled query, or a title Deezer
does not carry, returns whatever Deezer thought was closest and the row is marked `found: true`.
The user gets a wrong song presented identically to a right one, and the README's promise that
"the output always lines up with what you asked for" quietly stops holding.

The README documents this as a known limitation, so it is a deliberate tradeoff rather than an
oversight, but it is cheap to improve substantially.

Suggested fix: request `limit=5`, normalise (casefold, strip diacritics and bracketed suffixes
like `(Remastered 2011)`), and score each hit's title and artist against the query tokens. Take
the best scorer, and when even the best is weak, either mark the row with a `matchConfidence`
field or fall through to `blankRow`. Costs one Deezer request per song, well inside a budget the
MusicBrainz throttle is already dominating. Also see extraction idea 4 below: MusicBrainz's own
recording `length` gives a free second opinion on whether the match is right.

### 6. New windows and in-page navigation are not blocked in the main process

**Severity: medium (security hardening)**
**File: `src/index.js:19`**

`webPreferences` sets only `preload`. `contextIsolation`, `nodeIntegration` and `sandbox` are all
at safe Electron 36 defaults, and `src/index.html:14` carries a tight CSP, so the current posture
is good. Two gaps remain:

- No `setWindowOpenHandler`. A `window.open` from renderer code is not governed by `frame-src`
  and would open a real BrowserWindow with no CSP of its own.
- No `will-navigate` guard. Nothing stops the window navigating away from `index.html` to a
  remote origin, at which point the preload bridge is exposed to that origin.

Neither is reachable today because no renderer code calls `window.open` or assigns `location`.
That is exactly the argument the CSP comment already makes for itself: it exists as the backstop
for the day someone adds a field and forgets.

Suggested fix: `win.webContents.setWindowOpenHandler(() => ({ action: 'deny' }))`, and a
`will-navigate` listener that calls `preventDefault()` for anything that is not the local
`index.html`. Set `sandbox: true` and `contextIsolation: true` explicitly in the same block so
the posture survives a future Electron default change. Ten lines total.

### 7. Titles containing commas are split into two songs

**Severity: medium**
**File: `src/text.js:26`**

`textToArray` splits on `,` and nothing else. `Hey, Soul Sister` becomes two queries, `Hey` and
`Soul Sister`, and both return confident wrong matches (compounding finding 5). This affects a
meaningful slice of real titles, and the README's own advice, that adding the artist name makes
matching far more reliable, pushes users toward `Song, Artist` phrasing that this cannot express
at all.

Suggested fix: split on newlines first when the input contains any, and fall back to comma
splitting only for single-line input. That preserves the documented comma behaviour, makes the
already-documented one-per-line style actually correct, and needs no UI change. Update the
`field__hint` in `src/index.html:44` and the README's "Using it" section to match.

## Auto-fixable

Low risk, mechanical, verifiable by the existing suite. Listed rather than applied because the
request was for a plan; say the word and I will do these on a branch.

### 8. `musicbrainz.js` at the repo root is a byte-identical duplicate of `src/api/musicbrainz.js`

**File: `musicbrainz.js`**

`diff` reports the two files identical. It was committed by accident in `12eff91`
(`feat: fetch mood and danceability during a lookup`). Nothing requires it: `src/api/lookup.js:6`
resolves `./musicbrainz.js` relative to `src/api/`. Because `forge.config.js` sets no packager
`ignore`, it is bundled into the shipped asar on every platform.

The risk is not the bytes, it is that the next person to fix a ranking bug has two files to find
and will edit the wrong one. Delete it.

### 9. `blankRow` has no `error` key

**File: `src/api/lookup.js:12`**

`error` is attached ad hoc at `lookup.js:91` only on the failure path, so the row shape is not
uniform. `export.js:45` compensates with `row.error || null`. Adding `error: null` to `blankRow`
makes every row the same shape and lets the exporter read the field plainly.

### 10. `median` rounds even-length results but not odd-length ones

**File: `src/analysis.js:63`**

`median([1,2])` returns `2` (rounded from 1.5); `median([1,2,3])` returns the raw element. For
durations the inputs are whole milliseconds so the asymmetry is invisible, and `medianBpm` at
`analysis.js:191` rounds again on top. Harmless today, but it means the function's return type
depends on input length, which will bite the first caller that does not round afterwards. Round
in one place or neither, and cover both parities in a test.

## Test coverage gaps

The suite is genuinely good: 119 tests, network fully stubbed, no extra dependencies. Three
areas are untested because they are currently untestable as written, which is worth noting since
findings 1 through 6 all land in them.

- **`src/index.js`** has no tests at all. The four IPC handlers contain real logic: the
  `open-external` scheme allowlist (`index.js:52`) is a security control with no test asserting
  that `file://`, `javascript:` and a scheme-relative `//evil.com` are all refused. Extracting
  the predicate into a tiny pure module would make it testable in three lines.
- **`src/renderer.js`** has no tests. `renderSong` and `renderSummary` are pure string builders
  given a row, and hold the escaping guarantees. They could be exercised by exporting them the
  same dual CommonJS/global way `analysis.js` and `text.js` already do, which is an established
  pattern in this repo rather than a new one.
- **No end-to-end test through `lookupSongs`** with all three services stubbed together. The
  per-client tests are thorough, but nothing asserts that a Deezer hit with no ISRC falls
  through to MusicBrainz search, resolves a recording, and reaches AcousticBrainz with that
  recording id. That chain is the whole product.

## Further data worth extracting

Grouped by what it costs, because the request budget is the real constraint here and the README
is explicit that MusicBrainz sets the pace.

### Free: already inside responses the app fetches and discards

**1. Deezer track detail** (`/track/{id}`, already fetched at `deezer.js:207`)

- `rank`, Deezer's popularity score, 0 to 1,000,000. Gives a mainstream-versus-obscure axis the
  app has no equivalent of, and a "most and least known song in this list" summary cell.
- `gain`, ReplayGain in dB. This is real measured loudness, not a classifier guess, and it is the
  honest answer to the energy gap the README explains at length. A loudness spread across the list
  also reads directly as loudness-war era detection.
- `explicit_content_lyrics` and `explicit_content_cover`, four-value enums where the app currently
  keeps only the `explicit_lyrics` boolean. Distinguishes "explicit", "unknown" and "edited", and
  the app currently folds "unknown" into false.
- `contributors[].role`, Main versus Featured. `creditedArtists` at `deezer.js:120` reads the
  contributors array already and throws the role away, so the app cannot tell a lead artist from
  a guest. Adding it makes the distinct-artist count in the summary much more meaningful.
- `preview`, a 30 second MP3 URL. Would need CSP and `media-src` changes to actually play, so it
  is worth exporting even if not played.
- `available_countries` and `readable`, availability footprint.

**2. Deezer album detail** (`/album/{id}`, already fetched and cached at `deezer.js:189`)

- `label`, the record label. Entirely absent from the app today, and label concentration across a
  list is one of the more interesting things you can say about a collection.
- `upc`, `nb_fan`, album-level `duration`.

**3. MusicBrainz recording lookup** (already fetched with includes at `musicbrainz.js:227`)

- `disambiguation`. This is the highest-value free field in the whole audit. MusicBrainz uses it to
  mark a recording as `live`, `remix`, `acoustic version`, `radio edit`, `instrumental`. The README
  calls matching best-effort and warns that an ambiguous query can land on a live version; this
  field says so outright, on the row, at no cost. It also feeds a "how many of these are the actual
  studio recordings" summary cell.
- `length`, MusicBrainz's canonical recording duration. See idea 4.
- `video`, flags a recording that is a video rather than an audio track.

**4. Duration cross-check as a free wrong-match detector**

Comparing MusicBrainz `length` against Deezer `durationMs` costs nothing (both are already in
hand) and catches the failure mode findings 5 and 7 create. A studio original and the live version
of the same song rarely agree within a few seconds. Flagging rows where the two disagree by more
than roughly 5 seconds surfaces exactly the rows a user should check by hand, and needs no new
request at all.

### Nearly free: bigger response on a request already being made

**5. Extra `inc` parameters on the recording lookup** (`RECORDING_INC`, `musicbrainz.js:17`)

MusicBrainz charges per request, not per byte, so these ride along on the call at `musicbrainz.js:227`
with no extra second of throttle:

- `artist-rels`, which yields producer, engineer, mixer and performer credits with instruments.
  A whole production-credits dimension the app has nothing of.
- `artist-credits`, giving artist MBIDs and join phrases, so artists become identities rather than
  strings and the summary's distinct-artist tally stops splitting on spelling.
- `url-rels`, giving Wikidata, Discogs, Wikipedia and official streaming links per recording.
- `isrcs`, every ISRC MusicBrainz holds for the recording, not only the one Deezer served. Directly
  useful given the remaster-shares-an-ISRC problem documented at `musicbrainz.js:194`.
- `labels` on the releases, a second opinion on Deezer's label.

Worth watching the response size; `releases` on a popular song is already large, so measure before
adding all of them.

**6. Cover Art Archive**

The release group MBID is already resolved by `canonicalReleaseGroup`. The front cover URL
`https://coverartarchive.org/release-group/{mbid}/front` is constructible with zero requests, and
is the canonical artwork for the original release rather than whichever reissue Deezer served.

### One extra request per song

**7. AcousticBrainz low-level** (`/{mbid}/low-level`, sibling of the `/high-level` call at `acousticbrainz.js:128`)

- `tonal.key_key` and `tonal.key_scale`, the musical key, for example A minor. This is the single
  biggest musical fact the app is missing. It reports tempo but not key, and key distribution
  across a list, or Camelot-wheel compatibility for a set, is the kind of analysis people actually
  build playlists on.
- `rhythm.bpm`, AcousticBrainz's own tempo. Fills Deezer's gaps (the README notes Deezer has no
  tempo for every track) and cross-checks the ones it does have.
- `lowlevel.average_loudness`, `rhythm.beats_count`, `lowlevel.dynamic_complexity`,
  `tonal.chords_key` and `tonal.chords_scale`, `tonal.tuning_frequency`.

The cost is genuinely low: it only fires for recordings already known to be in the archive, and
lands inside the MusicBrainz gap the run is waiting out anyway, exactly as the existing
AcousticBrainz call does per the comment at `lookup.js:60`.

**8. High-level classifiers currently unread but already in the fetched response**

`extractFeatures` at `acousticbrainz.js:100` reads nine of the classifiers in a payload that
carries more. `acousticbrainz.js:33` documents skipping genre and gender, and that reasoning is
sound and should stand. It does not extend to:

- `timbre`, bright versus dark.
- `tonal_atonal`.
- `mood_mirex`, a five-cluster mood model, a useful cross-check on the binary mood classifiers.
- `ismir04_rhythm`, rhythm style (ChaChaCha, Jive, Waltz and so on).

These are free, in the same response, and follow the exact same `all`-versus-`probability`
extraction the module already gets right.

### One extra request per distinct artist, cached across the run

**9. MusicBrainz artist lookup** (`/artist/{mbid}`)

Needs `artist-credits` from idea 5 first. Yields origin country and area, artist type (Person
versus Group), and active years. Lists repeat artists heavily, so an instance cache like the album
cache at `deezer.js:181` keeps this cheap. Enables a geographic spread and an artist-era summary,
both new dimensions. Note that MusicBrainz also exposes artist gender; there is no analytical
reason to collect it and it should be left alone.

### One extra request per run, for the whole list

**10. ListenBrainz popularity** (`https://api.listenbrainz.org/1/popularity/recording`)

Open, no key, same MetaBrainz family as MusicBrainz, and it takes a **batch of recording MBIDs in
a single POST**. One request for an entire list returns `total_listen_count` and `total_user_count`
per recording. That is a platform-neutral popularity signal, a better one than Deezer's `rank` for
comparing songs, at a cost that rounds to zero. Best value-per-request on this list by a wide
margin.

### New summary cells these unlock, with no further data

- Key distribution and Camelot compatibility (needs idea 7)
- Loudness spread and loudness-war era (needs `gain`, idea 1, free)
- Label concentration (needs idea 2, free)
- Popularity spread, mainstream versus deep cuts (idea 1 or 10)
- Version purity, how much of the list is live, remix or remaster (needs `disambiguation`, idea 3, free)
- Geographic spread of artists (needs idea 9)
- Lead versus featured artist breakdown (needs `contributors[].role`, idea 1, free)
- Suspected mismatches, rows where Deezer and MusicBrainz durations disagree (idea 4, free)

## Suggested order

1. Finding 2 (timeouts), finding 1 (CSV injection), finding 6 (window handlers). Small, contained,
   and they close the three ways this can actually hurt someone.
2. Findings 8, 9, 10 (the auto-fixable cleanup) as one commit, since they are trivial and unblock
   nothing.
3. Finding 3 (IPC error envelope), then finding 4 (cancellation) on top of it, since both touch the
   same handler.
4. Finding 7 (newline splitting), then finding 5 (match scoring), in that order: fixing the splitter
   first removes a chunk of the wrong matches that scoring would otherwise have to catch.
5. Free extraction wins: `disambiguation`, `gain`, `rank`, `label`, `contributors[].role`, plus the
   duration cross-check. All zero-cost, all new summary dimensions.
6. Then ListenBrainz (idea 10), then AcousticBrainz low-level for musical key (idea 7).

Each step is independently shippable and testable. The test-coverage gaps are worth closing
alongside step 1 rather than as a separate pass, since the extractions they need (the URL
predicate, the renderer builders) are prerequisites for testing those fixes anyway.
